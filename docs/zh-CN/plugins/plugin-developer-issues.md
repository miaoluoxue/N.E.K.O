# 插件开发问题:主程序侧限制汇总

> 本文汇总了针对当前宿主 SDK 开发插件时遇到的问题。每一条都是插件无法在自身
> 进程内完全绕过的宿主侧限制, 报告出来供插件层反馈给主程序改进。已有对应 PR
> 的条目会附上链接。

## 1. 图片无法可靠显示在聊天窗(影响最大)

**现象。** 通过 `push_message()` 推送的图片 parts 行为不一致:

- `ai_behavior="blind"` 时, 宿主直接丢弃图片——用户完全看不到。
- `url` 形态的图片 part 会被 `main_server` warn-drop; 只有 inline `base64`
  形态能进模型视觉, 且仅限 `respond`/`read`。

**插件被迫的绕路方案。** 要让用户看到图片, 插件只能:

- 把图片写入自己的 `static/` 目录, 推 `markdown` 链接(`![alt](http://...)`)
  让前端渲染成图片气泡; 或
- 在插件自身状态里保存图片字节, 由插件自己的输出管线推送(而宿主对此没有
  官方通道)。

两种方式都让插件重复实现了宿主本应提供的资源管理、URL 编码和文件生命周期。

**相关 PR。** [#2835](https://github.com/Project-N-E-K-O/N.E.K.O/pull/2835)
(插件图片上传 + 受控投递)和 [#2905](https://github.com/Project-N-E-K-O/N.E.K.O/pull/2905)
(proactive media 渲染)都针对此问题。合并任一个即可让插件推送 canonical
image part, 替代上述绕路方案。

**请求的宿主能力。** 为插件提供一等公民的图片通道, 支持「显示到聊天窗」与
「喂给模型视觉」独立控制, 且 `visibility` / `ai_behavior` 的拆分行为文档化、可靠。

## 2. 双重回复:插件文本 + LLM 复述同一 summary

**现象。** 插件从 `@plugin_entry` 返回 `summary` 时, 宿主总是把它喂给主 LLM,
LLM 生成一条自然语言回复。如果插件自己已经把同一文本推送到聊天窗, 用户会
看到同一内容出现两次——一次原文、一次 LLM 转述。

**为什么插件无法完全修复。** 宿主没有「渲染给用户但不喂给 LLM」的开关。
插件侧的缓解是约定:「游戏只返回数据, 绝不自己推送用户可见文本」, 让 summary
成为唯一的用户可见副本。但 summary 仍会进 LLM 上下文, 插件无法完全抑制转述。

**请求的宿主能力。** 增加 `suppress_llm_reply` 标记(或让 `ai_behavior="blind"`
时 summary 不进 LLM 上下文), 让插件可以展示内容而不触发重复它的 LLM 轮次。

## 3. 游戏/长会话被宿主 proactive 消息打断

**现象。** 插件处于多轮会话(如游戏等待用户输入)时, 宿主或其他插件插入一条
proactive 消息进入 LLM 上下文。LLM 可能误以为会话已结束; 用户随后的命令(如
「继续」)被当成普通聊天, 而不是路由回插件的工具。

**插件被迫的绕路方案。** 每约 20 秒重新注入一条「会话状态锚」(只读文本告诉
LLM 会话仍在进行), 这很脆弱, 且覆盖不了「宿主恰好在用户下一条命令前插入
消息」的情况。

**请求的宿主能力。** 要么 (a) 当插件声明了活动会话时, 给 proactive 消息附带
「会话进行中」提示; 要么 (b) 暴露宿主级会话 API, 插件可标记活动状态并获
得路由优先级。

## 4. LLM 工具路由不可靠

**现象。** 插件的 LLM 工具(如 `play_game`)是否被调用完全取决于 LLM 的判断。
用户说「重启人生」(游戏名)时, LLM 可能先口头确认(「要开始玩吗?」)而不
调用工具, 游戏从未启动。

**插件被迫的绕路方案。** 强化工具描述 + 扩充关键词列表, 有帮助但不能强制路由。

**请求的宿主能力。** 支持插件声明「高优先级路由关键词」: 用户输入命中声明
的关键词时, 宿主确定性路由到插件工具, 而不是留给 LLM 自由裁量。

## 5. 插件没有宿主消息监听入口

**现象。** 没有类似 `@message` 的事件让插件实时响应宿主/聊天消息。文档中的
`on_owner_speak` 等宿主钩子从未被宿主调用, 插件只能靠 `tick` 轮询。

**插件被迫的绕路方案。** 每秒跑一次后台 tick 轮询, 浪费且增加延迟。

**请求的宿主能力。** 向插件暴露宿主消息事件(或真正调用文档中的
`on_owner_speak` 钩子), 让插件无需轮询即可响应。
